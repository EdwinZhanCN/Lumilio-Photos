# Lumilio Photos 26.1.0-rc.1

rc.1 is the first supported release of Lumilio Photos. From this version on,
your catalog, server configuration, backups, and the `.lumilioroot` /
`.lumiliorepo` markers in your media folders are upgraded in place by every
later version. Data written by the beta builds is **not** migrated; see
[Upgrading](#upgrading) before you install over a beta.

## Before you install

- **Desktop builds are verified on CI runners, not on a physical machine.**
  The macOS (Apple Silicon) and Windows (x64) apps in this release were built
  by the release workflow and verified by the automated Desktop test suites on
  GitHub-hosted macOS and Windows runners. No rc.1 Desktop build has been
  launched by a person on a real Mac or PC before publication. Treat Desktop
  as a release candidate in the literal sense: keep an independent backup of
  your media, and report anything that does not match this document.
- **Desktop has no in-app update in rc.1.** Settings → Updates reports that no
  signed update provider is configured. Updates are downloaded from the
  GitHub Releases page and installed over the existing app; in-app updates are
  planned for rc.2.
- **Network storage is not supported.** Storage Locations and Repositories on
  NFS, SMB/CIFS, AFP, sshfs, WebDAV, or a Windows network drive are refused,
  and the refusal cannot be confirmed away. Running Lumilio on a NAS with its
  media on local disks is supported.

## New

### Trash, Missing, and permanent deletion

- **Move to Trash moves the file.** Deleting a photo or video takes the file
  out of your folder and into that Repository's own Trash. Restore puts it
  back at its original path with its albums, rating, like, tags, description,
  and People intact.
- **The Trash is per Repository and expires.** Open it from the Storage page
  (per Repository, administrators) or from Collections → Trash. Trashed files
  are kept for 30 days and then deleted permanently; in Docker the period is
  `repository_trash.retention_days` in `server.toml`, Desktop uses 30 days.
  **Delete permanently** removes a trashed file now.
- **Duplicate resolution frees space.** The duplicates you do not keep are
  moved to the Trash instead of being hidden; the space is released when they
  expire or you delete them permanently.
- **Missing files are hidden, not shown as broken.** When a file disappears
  from disk (an unplugged drive, a deletion in Finder or Explorer), the photo
  leaves browsing, search, albums, and the Storage counts, and the
  Repository's **Missing** view on the Storage page lists it. When the same
  file comes back, the photo returns with its metadata. **Remove missing
  items** forgets missing files without touching the disk.
- **Editing a file in another app keeps its metadata.** Rewriting a file in
  place, including a metadata-only XMP or EXIF write, keeps albums, rating,
  like, tags, description, and People on the photo, and its thumbnails are
  regenerated.
- **A backup from before a deletion restores into the Trash.** Restoring such
  a backup lists the deleted file in the Trash, where you can restore or
  delete it, instead of reporting it missing.
- **A Repository you open again keeps what it carried.** Opening a Repository
  that already has a Trash, Studio edits, or unfinished uploads from an
  earlier installation no longer sets them aside. Its Trash is listed and
  **held**: those files never expire on their own until you restore them,
  delete them permanently, or choose **Keep with normal retention**. Studio
  edits are attached to their photos again once the scan has proven the
  content; anything that cannot be proven, plus unfinished uploads and
  unknown files, is listed in the Repository's **Recovery inventory** on the
  Storage page, where you can export or delete each item explicitly.

### Scanning

- Rescans compare each file's size and modification time with the scan
  index; unchanged files are not read again, and files or folders that were
  renamed or moved keep their identity and metadata without being hashed
  again.
- Each Repository is verified periodically (every 300 seconds by default;
  `repository_scan.interval_seconds` in Docker), and file-system change
  notifications are used where the platform provides them.
- The Storage page shows scan progress and counters, the scan history, and
  **Scan now** / **Cancel scan** per Repository.

### Storage page

- One Storage page for administrators groups Repositories by Storage
  Location, with capacity reported per Repository, scan status and history,
  **Rename Repository**, **Remove from Lumilio** (the folder and its files stay
  on disk), **Detect duplicates**, **Detect stacks**, and **Download support
  bundle**.
- **Add Repository reviews the destination first.** Lumilio assesses the
  chosen Storage Location and folder (file system, removable volume,
  permissions, existing markers) and lists the risks; you acknowledge each
  risk before the Repository is created, and the review is repeated if the
  disk changed in between. Unsupported destinations, network storage among
  them, are refused with the reason before anything is written.

### Music

- A **Music** section for your audio files: tracks, Music Albums, artists, and
  playlists, with a player dock that keeps playing while you navigate, a queue,
  liked tracks, and full-screen lyrics. Metadata corrections never rewrite
  the audio files.
- Lumilio Agent can search your music, audition tracks, and create or extend a
  playlist after your confirmation.
- Events are built from photos and videos only; audio belongs to Music.

### Processing view

- Monitor → **Processing** shows every pipeline stage as a card with its
  queued, running, and failed counts, lets you retry failed items, and shows
  diagnostics for a stage.

### Export photo

- One **Export photo** dialog from the viewer and from Studio, with shared
  format, quality, size, and file-name settings.

### Lumilio Agent

- The chat transcript of a tab survives a page reload for as long as the
  server keeps the conversation's memory (two hours of inactivity), and a
  pending confirmation is not lost by a reload.

## Fixed

- The Storage page showed wrong asset counts per Repository.
- A full search-index rebuild could report completion while the previous
  run's results were still being replaced; progress now comes from the
  rebuild itself.
- Edits to an Event (name, cover, membership) could be reverted by a
  background Event rebuild.
- Signing out opens the login page only after the session is closed, instead
  of resetting the login form midway.
- Audio and video playback no longer hangs when the web-friendly transcode
  finishes while the original is playing.
- A server that cannot read its share-link secret reports it at startup
  instead of failing at the first share.

## Known issues

- **Desktop in-app updates** are not available; download new versions from
  GitHub Releases (planned for rc.2).
- **Network storage** is refused for Storage Locations and Repositories.
- **Embedded cover art in audio files is not shown.** Tracks use a
  placeholder, and choosing an audio file as an album cover fails.
- **Case-only renames after moving a catalog between operating systems.**
  A catalog restored from macOS or Windows onto Linux, or the reverse, keeps
  file names compared under the previous system's rules; a file whose name
  differs only by letter case may be registered as a new file on the next
  scan.
- **Removing a very large Repository** blocks other catalog writes until the
  removal finishes.
- **Share controls lack accessible names.** The Share, Studio, and Add to
  album buttons in the export dialog, and the tiles of a public share, are not
  announced by screen readers.
- **A share's ZIP download includes original files** whenever downloads are
  allowed, even if the share's "include originals" option is off.
- **Registration stays open after setup.** Anyone who can reach the sign-in
  page can create a regular account; there is no invitation code or switch to
  close registration. Do not expose an instance to the internet without
  restricting access in front of it.
- **Backups are restored from the server's backups folder only.** The
  download button gives you the SQLite snapshot as a copy; there is no way to
  upload a backup file for restore.
- **Cloud import** supports iCloud only and is a one-way import, not a sync.
- **Platforms.** Desktop is published for macOS on Apple Silicon and Windows
  x64 only; Linux runs the Docker Server; there is no mobile app.

## Upgrading

### Coming from a beta build

rc.1 does not open a catalog, configuration, or backup written by a beta
build (`v1.0.0-beta.*`, `v26.1.0-beta.*`); it names such a file as
pre-release and stops. Albums, People, ratings, Event names, and share links
from the beta are not carried over. Your media files and the Repository
folders are untouched, and rc.1 reads the markers the beta wrote.

1. Create a database backup in the beta build if you want to keep it for
   reference, and back up your media independently.
2. Stop the beta build. Move its application state aside (Docker: the
   `LUMILIO_STATE` directory; Desktop: the `Lumilio Photos` folder under
   your user's application-data directory). Do not delete the media folder.
3. Move the beta's Primary Repository folder (`primary/` inside the Default
   Storage Location) to another name inside the same Storage Location, for
   example `beta-primary/`. rc.1 setup creates a new Primary Repository at
   `primary/`.
4. Install rc.1 and complete the first-run setup.
5. On the Storage page, add the renamed folder back as an existing Repository
   and let the scan register its files. Repeat for any other Repository the
   beta used.

### From rc.1 on

- When a new version changes the database, startup first writes a
  `pre-upgrade-…` snapshot to the backups folder (kept out of retention and
  listed as a restore point), then upgrades the database. A failed upgrade
  step stops the server and names the step and the snapshot.
- The server never rewrites your `server.toml`. When its format changes,
  startup stops and asks you to run
  `docker compose run --rm lumilio server config upgrade --config /data/app-state/server.toml`,
  which saves the previous file as `server.toml.bak`. The default Docker
  profile's configuration is built into the image, and Desktop upgrades its
  own configuration; neither needs this step.
- An older version refuses a database, backup, or configuration written by a
  newer one; roll back with the pre-upgrade snapshot.

Full steps for Desktop and Docker:
<https://docs.lumilio.org/user-manual/introduction/upgrade> (English) and
<https://docs.lumilio.org/zh-cn/user-manual/admin/upgrade> (中文).

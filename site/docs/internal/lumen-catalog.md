# Lumen Hub catalog pin (`lumen.lock.json`)

The Desktop embeds a pinned Lumen Hub release (URL + SHA-256 per profile) and
the published Docker Compose files select Lumen presets. Both must agree with
the Hub release catalog, so this repo keeps a single version source of truth:

- `lumen.lock.json` (root) — schemaVersion 1. Only **`release`** (a Hub GitHub
  Release tag like `v0.1.1`) is hand-edited; Renovate updates it via the
  `github-releases` datasource in a dedicated PR with automerge disabled.
  `revision` (tag commit) and `manifestSha256` (SHA-256 of the release's
  `manifest.json`) are derived data written by `task lumen:sync`.
- `desktop/internal/lumen/release_catalog.go` — generated code: the pinned
  `OfficialReleaseVersion` and the four Desktop artifacts
  (`darwin-arm64-metal`, `darwin-arm64-cpu`, `windows-x64-cpu`,
  `windows-x64-gpu`). Generated by `task lumen:sync`; never hand-edit.

## Commands

```text
task lumen:sync     # fetch pinned release manifest + SHA256SUMS, verify,
                    # refresh lock derived fields, regenerate the Desktop catalog
task lumen:check    # same verification without writes (CI gate)
```

Both are `server/tools/lumenlock` (`go -C server run ./tools/lumenlock
<sync|check> <repo-root>`). They verify:

1. `manifest.json` parses (schemaVersion ≤ 2; v0.1.1-era legacy manifests are
   accepted) and its `version` equals the locked release.
2. `SHA256SUMS` (legacy releases: `checksums.txt`) covers `manifest.json`
   itself and every hub artifact with a matching digest.
3. Consumer builds: all four Desktop profiles exist in the catalog, and every
   `LUMEN_PRESET` referenced by `deploy/compose/lumen-*.compose.yml` is
   defined by the manifest.
4. The tag resolves to `revision` via `git ls-remote` and the manifest hashes
   to `manifestSha256`.

## Hub upgrade flow

1. Renovate opens a PR bumping only `lumen.lock.json` → `release` to the new
   Hub tag. `lumen:check` fails on that PR (derived fields are stale by
   design) — that is the signal.
2. A maintainer runs `task lumen:sync` locally, which updates `revision` +
   `manifestSha256` and regenerates `release_catalog.go`, and pushes the
   result to the PR branch.
3. `lumen:check` goes green; the PR is merged by a human (never automerged).
4. Desktop builds from then on embed the new Hub release (Hub releases first,
   Photos after).

The Hub release manifest (`schemaVersion: 2`) is generated from
`lumen-schema` at release time and contains the four capability Exact Terms,
preset/custom options, model/dataset options, resource guidance, dist
platforms, artifact digests, and protocol provenance. Site and Desktop consume
it; no parallel constants are maintained.

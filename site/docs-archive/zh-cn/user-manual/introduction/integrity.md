# 备份与数据完整性

一份可恢复的 Lumilio 备份至少要同时覆盖 **原始媒体** 与 **SQLite 目录中的应用目录数据**。缩略图、搜索索引和模型缓存可以重建，但它们不能替代前两者。应用内的数据库备份只包含相册、人物、编辑等目录数据，**不包含媒体文件**。

## 在应用中备份数据库

<DocPath :items="['设置', 'Server', '数据库备份']" />

管理员可以启用自动备份、设置间隔和保留数量，也可以立即创建、下载、删除或恢复一个快照。新资源库默认启用自动数据库备份，默认间隔为 24 小时、保留最近 14 份；这些值可以修改，也可能在迁移后不同，因此以此页面当前显示为准。

Desktop 的本机备份目录可在 **Desktop 控制面板 → 路径** 查看。Server 的备份目录由完整 TOML 中的 `storage.backups_path` 决定。下载一份数据库快照到另一块设备，才能避免应用数据盘同时损坏时连备份一起丢失。

## 推荐做法

- 原始媒体至少保留两份，且其中一份不与主设备长期连接；
- 使用 **设置 → Server → 数据库备份** 创建一致快照；只有在服务完全停止后才直接复制数据库目录；
- 记录资源库与存储位置的对应关系；
- 定期实际执行恢复演练，而不只是检查备份任务显示“成功”；
- 在升级、批量删除和移动磁盘前额外创建恢复点。

::: danger 不要复制正在写入的 SQLite 文件
直接复制运行中的数据库及其旁路文件可能得到不一致快照。优先使用在线备份机制；如果只能离线复制，先完全退出 Desktop 或停止 Server。
:::

回收站用于撤销误删，不是备份。RAID、同步盘和云盘也各自只能解决部分风险，不能替代独立、经过恢复验证的备份。

## 点击“恢复”后会发生什么

恢复是**异步操作**：点击**恢复**只是提交请求，服务器返回 `202 Accepted` 和持久化的 **operation ID**，此时恢复尚未开始，更不代表已经完成。

提交后，浏览器会跟踪以下阶段：

```text
staged（已暂存） → restart（重启） → install（安装）
→ verify（验证） → complete（完成）
                     └→ rollback / fail（回滚 / 失败）
```

- **staged**：备份已经复制到待安装位置，还没有动当前数据库；
- **restart**：服务进入受控重启，把暂存的数据库换上去；如果重启钩子不存在，暂存的恢复会被取消，**当前数据库保持不变**；
- **install**：新数据库成为当前数据库；
- **verify**：服务端验证新数据库是否可用；
- **complete**：恢复完成；
- **rollback / fail**：任何一步失败时，旧数据库会被恢复，而不是停在半坏状态。

**页面短暂断线属于预期行为**：重启期间浏览器到 Server 的连接会断开。不要反复刷新或重复提交恢复请求；记录下 operation ID，页面恢复后可以凭它继续观察同一操作的进展。

::: danger 恢复过程中不要干预
恢复期间不要关闭容器、删除媒体目录或再次点击恢复。验证失败时服务会自己回滚到之前的数据库；如果外部干预破坏了恢复现场，回滚也可能无法完成。
:::

在生产实例操作前，先创建最新恢复点，并确认没有导入或编辑任务正在运行。

## 备份不等于“整套可恢复”

- **应用内数据库备份只包含 SQLite 目录数据**（相册、人物、编辑记录、账户等），不包含原始媒体、缩略图缓存或模型缓存；恢复数据库后，媒体必须仍然在原位置可读；
- **同磁盘上的备份不能抵御磁盘故障**：备份目录与应用数据在同一块盘上时，磁盘损坏会同时带走两者。至少把一份数据库快照和一份媒体副本放到另一块设备上；
- 回收站用于撤销误删，不是备份；RAID、同步盘和云盘各自只能解决部分风险，不能替代独立、经过恢复验证的备份。

## 恢复演练

1. 同时准备一份数据库快照和对应的原始媒体备份；
2. 记录快照的创建时间、应用版本和资源库位置；
3. 在非生产实例中恢复数据库；
4. 确认能登录，并抽查相册、人物和媒体路径；
5. 打开多种格式的原始媒体，确认文件本身也能恢复。
